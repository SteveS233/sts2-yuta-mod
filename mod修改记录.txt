[2026-10-14 13:52] 修复：选中乙骨忧太后开局无效（会变成故障机器人）
  · 现象：角色选择界面能点选乙骨，但开始新局后角色是故障机器人
  · 根因：初始遗物「里香」没有加入任何遗物池，RelicModel.Pool 查找时抛
      InvalidOperationException: Sequence contains no matching element
    而这条语句位于 NCharacterSelectScreen.SelectCharacter 读取遗物描述的地方，
    排在 _lobby.SetLocalCharacter(角色) 之前 —— 异常一抛方法即中断，
    角色从未写入 lobby，于是开局沿用了上一位已选角色（故障机器人）
  · 修复：在 ModEntry.Initialize 中追加
      ModHelper.AddModelToPool<IroncladRelicPool, Rika>()
    让「里香」归属铁甲战士遗物池。其稀有度为 Starter，
    而 RelicFactory.RollRarity 只产出 Common / Uncommon / Rare，
    所以入池不会让里香出现在遗物奖励里
  · 本条的数值 / 效果未做任何改动

[2026-10-14 15:40] 根因查明：进入商店黑屏卡死（不是事件房间）
  · 现象：进入问号/商店房间时黑屏卡死
  · 日志证据（godot.log 第 613 行）
      System.InvalidOperationException: Can't generate valid rarity for merchant
      card type Skill with card options:
      调用栈：CardFactory.CreateForMerchant -> MerchantCardEntry.Populate
              -> MerchantInventory.PopulateCharacterCardEntries
              -> MerchantRoom.EnterInternal
  · 根因：乙骨卡池太小，填不满商店的卡位
      MerchantInventory 固定要开 5 个角色卡位：
        Attack, Attack, Skill, Skill, Power
      每个卡位 Populate 时会用 _cardPool.Except(已生成的卡) 剔除已用过的牌。
      当前池内非 Basic 的牌只有 3 张：2 攻击 + 1 技能 + 0 能力，于是：
        卡位1(攻击) 用掉 1 张攻击
        卡位2(攻击) 用掉另 1 张攻击
        卡位3(技能) 用掉唯一的技能牌
        卡位4(技能) 剩余为空 -> 抛异常   ← 与日志完全吻合
  · 结论：不是事件的问题，是商店；但「卡池太少」这个方向判断正确
  · 解除条件：卡池至少要有
      非 Basic 攻击牌 x2（现有 2，已满足）
      非 Basic 技能牌 x2（现有 1，缺 1）
      非 Basic 能力牌 x1（现有 0，缺 1）
  · 附注：卡牌奖励不会因此崩溃
      CreateForReward 的允许稀有度由当前池子实际内容推导，
      再配合 GetNextAllowedRarity 的向上取整 + 环绕，只要还有任意非 Basic 牌就能兜住
  · 本条为根因诊断，未改动任何游戏数值

[2026-10-14 15:43] 「模仿」夺取效果从「本场战斗」升级为「整局游戏持续」
  · 卡牌「模仿」
      改前：斩杀时，获得该敌人身上的所有正面效果（仅本场战斗有效）
      改后：斩杀时，本局游戏中获得该敌人身上的所有正面效果
  · 实现难点：游戏里的能力（力量、活力等）都是战斗内状态，战斗结束即清空，
    所以「整局持续」必须把夺取记录存到能跨战斗存活的地方，每次战斗重新挂载
  · 实现方式
      1. 遗物「里香」新增 [SavedProperty] string StolenBuffs，
         编码为 "能力ID=层数;能力ID=层数"（能力 ID 用 ModelId.ToString()）
      2. 模仿斩杀时：当场挂一份 + 调用 Rika.RecordStolenBuff 记录（同能力累加层数）

[2026-10-14 17:45] （待定议题，非改动）「模仿」斩杀收益的设计讨论
  · 用户提出：有特殊 buff 的敌人太少，希望每次斩杀都有不同收益
  · 诊断（若以后重启此议题，直接从这三条结论开始）
      1. 根本问题不是「收益不够」，而是触发与否取决于玩家无法控制的事实

         即使机制改对了，不加可见反馈也白搭。这一条独立于机制改动，值得单做
      3. 「每次都有收益」与现有的跨战斗累积框架正面冲突：
         累积速度会暴涨，正是当初排除力量的原因。
         必须先决定防滚雪球方案：收益不累积 / 设总量上限 / 高收益只首次给

      PowerType.Buff 的能力共 200 个，取材充足
      RoomType 现成提供 Monster / Elite / Boss 三档，可用于按敌人强度分档

      1. 随机必须用游戏自身的种子随机源（player.RunState.Rng.*），
